### 已复现并修复：新实验目录初始化失败

同步和异步入口先 `makedirs(checkpoint_dir)`，随后 `initialize_checkpoint_dir` 检查同一目录；新运行未指定 resume/overwrite 时必然报 FileExistsError。作者基线也有这段逻辑，pick 示例默认带 resume 因而避开；UR 新运行命令没有 resume，暴露了冲突。此前四卡诊断直接构建模型，没有执行正式输出目录初始化，因此没有覆盖它。

本轮删除两个入口提前创建 checkpoint 目录的语句，交由原初始化函数统一创建。已有目录仍拒绝无显式 resume/overwrite 的启动，不通过自动覆盖绕过保护。真实同步 CLI 在临时目录复现失败；新增回归直接执行两个入口的目录初始化片段，修复前均失败，修复后新目录成功、已有目录拒绝，完整 43 项回归通过。未重新执行 GPU 模型测试，未启动机器人。

### GPU 0：计算调度与显存分别看待

同步入口 mesh 使用 GPU 0–3，Pi05 rollout 推理副本放 GPU 0。`delay=0` 时 AsyncChunkSampler 不启动后台推理，直接调用 sample_actions；episode 结束后主线程调用更新，后续动作推理依赖更新后的参数。因此没有一个独立 rollout actor 在训练过程中持续对 GPU 0 做模型 forward。后台线程用于机器人 reset 和 batch 预取；预取可能涉及数据转换/传输，不等于第二路策略推理。JAX 异步 dispatch 也不能把这套数据依赖关系理解成独立 actor/learner 并行。

参数、优化器状态、推理缓存和 XLA 分配仍共享显存，顺序执行不代表推理阶段训练状态释放。`cache_infer_params` 包含 actor_train_state 与其他推理参数，GPU 0 的压力需要计入；上一轮四卡默认 batch64/UTD20 测试通过、运行快照约 60.3 GiB/卡，仅证明该短跑可运行，不保证长跑峰值。

作者另有异步入口，将首卡给推理、其余可见卡给训练；它与当前同步入口不同。本轮不切换。若使用全部四卡切到该异步入口，训练卡数变为 3，而 batch64 不能被 3 整除，会触发参数检查，不能只改脚本文件名就认为配置可用。

### 尚存问题：异常恢复不能视为可靠续跑

`EnvClientWrapper._call` 遇 RuntimeError 后重建环境；对于非 reset 操作会连续调用两次 reset，随后重试原 thunk。Mock 检查复现 step 失败后在新 env 上重发旧动作，调用方收到普通成功。外层 learner 的 action_plan、EpisodeSink 和 episode 计数没有收到环境重建通知，可能把重置前后的状态写进同一条轨迹；UR 还会出现重复复位确认。这是作者通用恢复代码已有的问题，UR 本地断线清理并不能修复服务器的轨迹边界。本轮未擅自改变恢复策略，不能声称断线恢复已经验证；需要单独实现“错误终止本次采集”或明确的 episode 截断/重连协议后，再做故障注入验证。证据：[无硬件恢复复现](logs/server-recovery-audit-20261116.log)。

### 归档与 resume 的静态检查边界

`ur_run.json` 记录模型配置、执行长度、归一化哈希、Python 源码指纹等，但未收集机器人端实际 YAML 内容；仅看服务器记录不能证明本地 max_episode_chunks、工作空间、控制参数未被修改。resume 一致性检查也未比较已记录的 task_description。正式实验还需归档机器人端有效配置，不能把服务器上的 YAML 当作远端实际使用的证据。本轮记录该缺口，没有改变训练算法或偷偷采用 RLinf 的学习流程。

核心算法、Pi05 更新、BatchProcessor、replay 采样与损失仍沿用作者版本；成功 reward=1、其他=0，done 时 mask=0 的语义与作者 DROID 一致，没有套用 RLinf 的 truncation/bootstrap 规则。真实大模型 checkpoint 保存/恢复及长时间运行仍未覆盖，小参数 Orbax 回归通过不代替该项。
