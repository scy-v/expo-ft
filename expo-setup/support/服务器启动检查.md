## 在线 RL 的 GPU 分配及 LoRA 学习率修正（2026-11-16）

“在线 RL”描述使用交互数据更新策略，不要求采集和训练同时运行。`client.run_client` 是机器人环境客户端，只采集图像/状态、执行服务器动作和处理接管；Pi05 主策略、edit actor 与 critic 都位于服务器。本地 actor 这个部署名称不代表本地运行模型网络。

| 作者入口 | 可见 GPU 默认值 | 梯度更新 | rollout 推理 | 调度 |
|---|---|---|---|---|
| `scripts/pick/run_server.sh` → `train_pi_robo.py` | 0,1,2,3，共 4 卡 | 使用全部 4 卡组成 mesh | 第一张可见 GPU，即默认 GPU 0 | 达到更新门槛后按 episode 更新；推理和更新交替，更新可与机器人复位重叠 |
| `scripts/pick/run_server_async.sh` → `train_pi_robo_async.py` | 0,1,2，共 3 卡 | GPU 1、2 组成训练 mesh | GPU 0 独立推理 | 后台更新线程与主线程采样并行，发布新参数供采样使用 |

同步入口通过 `make_mesh(fsdp_devices)` 使用全部可见设备；默认 `fsdp_devices=1` 形成 batch=4、fsdp=1 的 mesh，参数复制、训练数据分片，不能将其解释为只用一张 GPU。`build_pi05` 将 `infer_device` 指定为 `jax.devices()[0]`，`sample_actions` 使用单设备推理副本，因此同步 GPU 0 同时属于训练设备集合。异步入口显式使用 `jax.devices()[1:]` 训练，才将推理卡排除在训练 mesh 外。该异步在线入口与 Real-Time EXPO 是不同的概念，本次没有切换入口。

上述依据为 `train_pi_robo.py` 的 mesh/episode 更新、`train_pi_robo_async.py` 的设备选择/后台线程、`expo_ft/agents/vla/pi05.py` 的 infer_device、`expo_ft/agents/alg/expo_ft.py` 的推理副本刷新及 OpenPI `training/sharding.py`；均为静态源码核对，不代表四卡训练性能实测。本地 UR 启动文档仍指定单卡 GPU 0，同卡交替训练和推理；本次未修改 GPU 数、max_steps 或预测长度。

UR LoRA 分支此前总是从 full 配置继承优化器日程，是适配遗漏。已修改 `expo_ft/agents/vla/ur5e_data.py:make_train_config`：`lora=True` 继承作者 LoRA 配置，Pi05 学习率恒为 `2.5e-5`；`lora=False` 仍继承 full 配置，保持 `5e-5`。初始化 checkpoint 是全参还是 LoRA，和在线阶段选择哪种训练架构是两件事；全参 SFT 权重用于加载基础模型，不应导致在线 LoRA 误用 full 学习率。edit actor 和 critic 的学习率仍为 `3e-4`，它们不是 Pi05 的学习率。

静态检查执行两个分支的配置名选择并解析固定 OpenPI 定义，确认两条学习率日程及显式 UR 字段覆盖后仅 lr_schedule 改变；Python/命令语法检查通过，见[日志](logs/ur-lora-config-fix-20261116.log)。本地 actor 环境没有 JAX，未导入真实 TrainConfig 或进行 GPU 前向/梯度；服务器使用修正值前需同步源码。这次没有加载权重、连接机器人或启动训练。
