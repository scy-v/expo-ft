发现30次plan超过1000ms：29次与更新完成记录处于同一step，1次相距2step。最长停顿step4763的plan为3632.55ms，对应更新16；例如step8406对应更新30、step15342对应更新56。现有记录将这些秒级停顿定位到服务器plan，并与更新完成强相关，不能归因于这几次的相机或动作RPC。优先怀疑更新后推理权重复制、GPU队列竞争；尚不能在缺少分段记录的情况下确定具体CUDA操作或锁。

W&B时间戳包含缓冲刷新延迟，关联采用记录的step而非上传时间。旧日志不覆盖所有局末开销，也没有分开每路相机和RTDE调用，因此不能排除其他阶段另有偶发停顿。

## 新增诊断

服务器 `configs/ur/rollout.yaml` 与本地 `configs/ur/insert.yaml` 均默认 `timing_diagnostics: true`（按用户测试要求开启）。两端使用更新后的配置重启后，写独立JSONL，不向W&B塞入大量细粒度事件；[启用流程](../训练命令.md#可选定位-rollout-停顿)。

| 事件前缀 | 用于定位 |
|---|---|
| `loop.*` / `inference.*` | step、观测、plan、Pi05输入处理／GPU执行／输出、critic编码与残差选择、device_get |
| `learner.network_update` / `learner.copy_inference_weights` | GPU更新完成与跨卡推理权重复制分别计时 |
| `learner.*lock*` / `rollout.take_published_weights` | buffer锁、权重发布和接收 |
| `learner.next_batch_and_upload` | 采样、预处理及设备上传提交 |
| `rpc.*` | 打包、发送、等待响应、解包；rpc_id匹配两端 |
| `camera.*` | 逐路相机read、图像resize和状态转换 |
| `robot.*` / `controller.*` | 位姿／速度／力／夹爪读取、I/O锁、动作确认、100Hz forceMode调用 |
| `episode.*` | replay插入、磁盘／W&B／checkpoint、复位及人工确认等待 |

开始／结束事件包含主机单调时钟、墙钟、进程／线程及可用的step/update/rpc_id。锁和读操作的组合span进一步慢时，可按内部子事件区分；100Hz控制线程不天然具有主线程的rpc_id。两台机器的单调时钟不可直接相减，跨机通过rpc_id匹配。

后台有界队列满时丢弃诊断事件并累计计数，避免控制线程等待磁盘；写盘失败记录错误并继续原流程。开启诊断会在GPU更新、推理和权重复制边界显式等待，避免把异步任务提交误当成任务执行完成。此同步会扰动调度，因此用于定位，不作为无诊断的性能基准。关闭时不增加GPU同步、不修改模型／奖励／数据／控制频率或保存触发规则。
