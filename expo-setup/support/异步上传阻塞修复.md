# 异步上传阻塞复现与修复（2026-11-17）

## 结论

已在无机器人的真实learner＋缓存观测推理中稳定复现，并通过修改大状态树的完成等待方式消除本轮三次秒级停顿。不是CPU图片归一化耗时；仅切到CPU、或开启显存预分配，均未解决。

当前JAX 0.5.3的 `jax.block_until_ready(tree)` 对多数组调用 `xc.batched_block_until_ready`。原代码把整个learner状态交给该接口，涉及模型、优化器等大量数组。Nsight捕获更新收尾时183次 `cuStreamCreate`、14次 `cuEventCreate`、59次 `cuLaunchHostFunc` 调用超过100ms，最长均约3.44秒；同进程rollout上传等待与之重合。独立进程在同一GPU上传最长4.27ms，主进程CPU心跳最大间隔98ms，进一步排除纯GPU算力不足或Python线程整体停止数秒的解释。

采用 `block_until_ready_serial` 对每个数组逐个等待，保留全部结果就绪的保证，避免同时发出大量就绪请求。网络完成后再构建推理权重缓存；大缓存和两个训练入口的最终等待也使用同一方式。诊断开关关闭时同样使用该路径。此修改不改变batch、UTD、网络、优化器、数据或权重同步内容；CPU打包方案保留，生产显存预分配仍为false。

## 测试条件

- 源码：`d20ca57aabef4310a309492311b8b9cb82f617ff` 加工作区修改；JAX/jaxlib 0.5.3、CUDA驱动580.178.04。设备为A800 80GB，物理0／1训练、2推理，可见顺序2,0,1。
- 模型与数据：全参SFT2500初始化在线LoRA，10条真实示教；batch64、UTD20、FSDP1。只将诊断replay容量减为4000，不写正式checkpoint或W&B。
- 推理：从示教10取32帧缓存观测，经过正式输入处理、PI05、critic／edit选择，结果转回CPU并验证有限值；每次推理后模拟0.8秒动作执行。每轮更新后发布真实新权重。
- 排除首次编译／预热；启用细分诊断。修复前后分别连续3轮更新。未连接机器人，不覆盖RPC、实时相机、100Hz控制或长时间真机训练。

修复前三次上传停顿为3318／3353／2792ms；修复后三轮更新为58.373／57.878／58.191秒。所有更新指标和动作均有限。权重复制仍约数百毫秒，但本轮未造成秒级推理停顿。

失败对照：保持原批量等待、仅开启90%显存预分配，第一轮仍出现3378ms上传等待；已停止该诊断，未改变生产分配配置。Nsight采集单独一轮，也复现1948ms上传等待；采集有开销，不与无profiler的主对照混算。

19项CPU回归通过，覆盖逐数组等待顺序／失败传播、诊断开关、输入包装、异步错误处理和终端显示。该对照确认本机当前配置下的等待方式是可修复触发点，不声称识别了CUDA驱动内部每一把锁，也不保证今后所有停顿都来自同一原因。

## 复现与证据

仅在GPU空闲时执行，两个命令顺序运行；输出目录必须未存在。真实模型构建及预热需要时间，不连接机器人。

```bash
cd ~/expo-ft
source expo-setup/activate.sh
CUDA_VISIBLE_DEVICES=2,0,1 XLA_PYTHON_CLIENT_PREALLOCATE=false XLA_PYTHON_CLIENT_MEM_FRACTION=0.90 python scripts/diagnostics/reproduce_async_stall.py --wait-mode batched --updates 3 --output /tmp/expo-stall-before
CUDA_VISIBLE_DEVICES=2,0,1 XLA_PYTHON_CLIENT_PREALLOCATE=false XLA_PYTHON_CLIENT_MEM_FRACTION=0.90 python scripts/diagnostics/reproduce_async_stall.py --wait-mode serial --updates 3 --output /tmp/expo-stall-after
```

`--wait-mode batched` 只在诊断进程恢复旧等待方式，不修改生产文件。`--profile` 供Nsight的cudaProfilerApi capture-range使用。正式训练沿用原命令和YAML。
